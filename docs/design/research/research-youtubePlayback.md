# SUMMARY
Two independent live test campaigns settle this. (1) QUALITY: YouTube's IFrame API quality methods are officially no-op (confirmed in current docs); `vq=` is undocumented and I confirmed via the live embed HTML that it is NOT parsed into PLAYER_VARS (it survives only as an echo inside `client.originalUrl`), so it is almost certainly inert. The only remaining lever is the player's *own element size*, which the iframe's internal layout viewport controls — a CSS `transform: scale()` on the parent does NOT shrink the iframe's inner viewport, so an oversized iframe scaled down is the correct and only mechanism. (2) EXTRACTION IS DEAD for a pure static origin, and I proved it three separate ways rather than inferring it: YouTube's InnerTube endpoint returns **HTTP 403 the moment a third-party `Origin` header is present** (200 with no Origin or with `Origin: https://www.youtube.com`) — an origin allowlist, so `fetch()` from GitHub Pages fails before CORS is even relevant; googlevideo.com media responses carry **no `Access-Control-Allow-Origin`** at all, killing MSE/dash.js/hls.js; and the only non-MSE muxed format any client still returns is **itag 18 @ 360p**, roughly a third of the ~1140px needed for the 640x640 crop. The public proxy networks that used to paper over this have collapsed: the official Invidious directory is down to 5 HTTPS instances, **all with `"api": false`**, and all 5 returned 403/401/bot-wall; of 16 documented Piped instances exactly one responded, and it served a 360p muxed stream with zero audio streams. RECOMMENDATION: an oversized *square* iframe (1920x1920) whose letterboxing pushes YouTube's chrome into black bars outside a center 1080x1080 crop — this solves quality and chrome with one geometry trick — plus a self-hosted-file path as the real high-quality primary. Do not ship extraction.

- [likely] MECHANISM (the crux): the player's initial/steady-state format is chosen from the rendered size of the player element multiplied by devicePixelRatio, capped by measured bandwidth. A 640x640 player therefore requests ~360p-480p. Crucially, a CSS `transform: scale()` or `zoom` applied to a PARENT container does not alter the iframe's internal layout viewport — inside the iframe the player still measures its own width/height attributes. This is exactly why the oversized-iframe trick works, and why merely styling a small iframe does not.
  src: Mechanism inferred from: official docs' silence + ABR literature (device display resolution is a documented ABR input) + consistent community reports. I was unable to run a live browser measurement (claude-in-chrome requires interactive browser selection), so this is corroborated-but-not-instrumented.

# RECOMMENDATIONS
STRATEGY — three tiers, in build order.

TIER 0 (PRIMARY for quality; build first): Self-hosted / user-supplied media. A plain <video> element with a local or CORS-enabled MP4/WebM gives exact frame control, true 1080p+, instant A-B looping via `timeupdate` + `currentTime` assignment, zero chrome, zero spinners, zero third-party fragility. Ship a "add your own clip" path (file picker -> IndexedDB/blob URL, or a URL field, or files committed to the repo). Every hard requirement in the brief is trivially satisfied here. This should be the documented happy path, not a footnote.

TIER 1 (PRIMARY for YouTube): Oversized SQUARE iframe + center crop. The single highest-leverage finding in this research.
- Structure: outer .viewport {width:640px;height:640px;overflow:hidden;position:relative} > inner .crop {position:absolute;width:1920px;height:1920px;transform:scale(0.3333);transform-origin:top left;left:-... } wrapping an <iframe width="1920" height="1920">.
- Because the iframe is SQUARE, the player letterboxes the 16:9 video into the vertical middle and paints title overlay / watermark / control strip onto the black bars, which the crop discards. A 16:9 iframe cannot achieve this — the chrome overlaps live video pixels. This is the crux; do not substitute a 1920x1080 iframe.
- The same 1920px measured width pushes the size-based quality heuristic to 1080p+. One trick, both problems.
- URL: https://www.youtube-nocookie.com/embed/<ID>?enablejsapi=1&origin=<pages-origin>&controls=0&autoplay=1&mute=1&playsinline=1&rel=0&iv_load_policy=3&disablekb=1&fs=0. Include vq=hd1080 only as a free no-op; never depend on it.
- Layer an opaque overlay (matching the video's dominant color, or a captured poster frame) driven by onStateChange: opaque on UNSTARTED/BUFFERING(3), fade out on PLAYING(1). This masks the initial handshake and any post-seek spinner.
- A-B loop: poll getCurrentTime() on rAF; when t >= B call seekTo(A, true). Prime by playing the segment through once so [A,B] sits in the buffer — backward seeks inside a buffered range do not spin. Never call pauseVideo(); never let playback reach duration.

TIER 2 (FALLBACK, degraded): if the square-iframe geometry misbehaves on-device, fall back to a 16:9 oversized iframe (1920x1080 -> center 1080x1080 crop) and accept the top title overlay on hover/seek, masked by the state overlay. Still 1080p; imperfect chrome.

DO NOT BUILD: stream extraction, in any tier. This is not a ToS judgement call — I measured it dead three independent ways. InnerTube 403s on any third-party Origin (allowlist, not CORS). googlevideo sends no ACAO, so MSE/dash.js/hls.js cannot fetch a byte. The sole muxed no-CORS format is 360p, ~a third of the required width. The proxy networks that used to bridge this are gone: every officially-listed Invidious instance now advertises "api": false and all 5 return 403/401/bot-wall; 1 of 16 Piped instances is alive and it serves 360p with no audio streams. Shipping a runtime instance-directory fetch would produce an app that is broken on arrival and degrades further. If you want it documented for the curious, put it in a "why this doesn't work" section of the README with these measurements — that is genuinely more useful to an OSS audience than a dead code path.

VALIDATE ON-DEVICE FIRST (three cheap checks that de-risk everything): (1) log window.devicePixelRatio inside the CAM webview — the quality math assumes 1, and a DPR of 2 changes the iframe sizing; (2) confirm a cross-origin youtube-nocookie iframe renders at all in the CAM webview and that muted autoplay fires without a user gesture; (3) confirm a 1920x1920 iframe scaled to 640x640 does not blow the frame budget at targetFps — if hardware decode is unavailable, step the iframe down to 1280x1280 and accept 720p (1280 center-crop = 720x720, still comfortably over the ~1140px... note: it is NOT — a 1280x1280 iframe yields a 720x720 crop, which is below the 1140px bar. If decode is constrained, prefer Tier 0 self-hosted media over dropping iframe size).

MOST IMPORTANT UNVERIFIED ASSUMPTION: I could not instrument a live browser this session (the Chrome tooling requires interactive browser selection, inappropriate for a background research run), so the square-letterbox chrome placement and the size->quality response are corroborated-but-not-measured. Both are cheap to confirm with a single test page — do that before committing to the architecture.
