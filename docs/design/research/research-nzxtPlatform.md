# SUMMARY
Canonical docs exist and were read in full (raw markdown from NZXTCorp/web-integrations-docs, plus official TS types from NZXTCorp/web-integrations-types). The platform contract is small and well-defined: CAM opens TWO Chromium browsers on the SAME origin — a visible "Configuration Browser" (your URL, no params) and a hidden "Kraken Browser" (your URL + `?kraken=1`) that is streamed to the LCD. They share session (localStorage/cookies/IndexedDB), which is the ONLY sanctioned config→display channel. CAM injects `window.nzxt.v1` with `{width, height, shape, targetFps}` and calls `onMonitoringDataUpdate(data)` at exactly 1 Hz if you assign that property. Kraken Elite = 640x640 circle; Kraken Z = 320x320 circle; Kraken (2023) = 240x240 square. THE SINGLE MOST IMPORTANT FINDING FOR A VIDEO APP: the LCD render frame rate defaults to 1 FPS and is a user-controlled slider in CAM (Lighting → Kraken → Web Integration → Frame Rate); Elite max is 40 FPS, Kraken (2023) max 25, Kraken Z will never be raised (NZXT staff statement). Further, NZXT staff confirm the Elite pipeline COMPRESSES frames, so achieved FPS varies with frame content — high-entropy video is the worst case. This, not raw resolution, is the mechanism behind the "YouTube looks bad" complaint. Also critical: Web Integration mode does NOT track navigations (no SPA routing/redirects on the Kraken browser), and the official landing-page code sample is subtly WRONG (it reassigns `window.nzxt` wholesale, clobbering CAM's injected width/height/shape/targetFps) — correct practice is property assignment onto the existing object, with retry because injection can be delayed. GitHub Pages static hosting is the norm and is the only form NZXT accepts for official submission.

# RECOMMENDATIONS
ARCHITECTURE CONSTRAINTS THAT MUST SHAPE THE DESIGN:

1. Single-entry, no-navigation SPA. CAM never follows navigations on the Kraken Browser. Ship one HTML entry; do all state changes in-place. No client-side router that changes the URL, no redirects, no meta-refresh. On GitHub Pages specifically, avoid a trailing-slash redirect on the configured URL — publish the canonical URL the user pastes (prefer `https://<user>.github.io/<repo>/` with a real index.html at that path).

2. Dual-mode single bundle. Branch at boot on `new URLSearchParams(location.search).get('kraken') === '1'`. kraken=1 → render the 640x640 display surface only. Otherwise → render the settings/config UI. Both are the same origin, which is what makes the shared-session channel work.

3. Config→display transport = localStorage + `storage` event (plus IndexedDB for blobs). The `storage` event fires cross-renderer because both browsers share the origin/session. Design settings as a single serialized JSON key so one write = one atomic update. Add a fallback poll (e.g. 1s) in case the storage event is unreliable in the Electron webview — cheap insurance, and NZXT-ESC's defensive style suggests the platform warrants it.

4. NEVER reassign `window.nzxt`. Do `window.nzxt = window.nzxt || {}; window.nzxt.v1 = window.nzxt.v1 || {}; window.nzxt.v1.onMonitoringDataUpdate = handler;` — assigning the object wholesale (as NZXT's own landing-page sample does) wipes CAM's injected width/height/shape/targetFps. Wrap in retry (immediate, then 200ms x10) because injection can land after load.

5. Read geometry, never hardcode. `const {width=640, height=640, shape='circle', targetFps=1} = window.nzxt?.v1 ?? {}`. Support 640x640 circle (Elite/Plus), 320x320 circle (Z), 240x240 square (Kraken 2023). Treat `shape` as `'circle' | 'square'` (official) and tolerate unknown values. When circle, inset a safe area (~6-10% radius margin) for anything text-like.

THE VIDEO PROBLEM — THIS IS THE CORE INSIGHT:

6. The bottleneck is NOT the 640x640 resolution, it is (a) the user-facing FPS slider defaulting to 1, and (b) content-dependent frame compression on the Elite. NZXT's engineer stated compression means "the actual frame rate might vary depending on the frame content," worst case being pre-update (i.e. very low). Full-frame, high-entropy video is the pathological input. Concretely this means:
   - Onboarding MUST tell the user to drag CAM's Target Frame Rate slider to max (Lighting → Kraken → Web Integration → Frame Rate). Without this they get 1 FPS and will blame our app. Consider detecting `targetFps <= a low threshold` on the Kraken Browser and rendering an on-screen prompt telling them to raise it.
   - Design for compressibility: prefer large flat color areas, limited palettes, static backgrounds with small moving regions, and avoid film grain / dithering / noise / rapid full-frame scene changes. A mostly-static layout with a small animated region will hold higher effective FPS than full-bleed video.
   - Adapt to `targetFps`: drive animation from a rAF loop gated to `1000/targetFps` rather than assuming 60. Degrade gracefully (drop to static frames) when targetFps is low.

7. Beat the official YouTube integration on its own terms. NZXT's official one is ~40 lines that iframes the YouTube embed player at 640x640 and applies `transform: scale(1.8)` to crop away letterboxing — so a 16:9 stream is upscaled ~1.8x then center-cropped into a circle. That is the whole "low resolution" complaint, and it also drags in ads/recommendation overlays (NZXT-ESC warns about exactly this, and eventually banned YouTube URLs outright in favor of direct .mp4). Our differentiators should be: (a) render the source at native 1:1 into the 640x640 square instead of scale-cropping, (b) prefer direct MP4 / user-supplied media over the YouTube iframe where possible, (c) if YouTube is required, use the IFrame Player API with `vq`/quality hints and a proper cover-fit that crops the minimum necessary, and suppress related/branding chrome.

8. Autoplay: always `muted` + `playsinline` + `autoplay`, and set `allow="autoplay; encrypted-media"` on any iframe. Assume unmuted autoplay is blocked (standard Chromium policy; NZXT's own example uses mute=1). Never rely on audio — and treat "does audio reach the speakers" as an untested unknown; if we ever add sound, gate it behind an explicit opt-in in the config UI and verify on hardware first.

9. Defensive liveness. There is precedent for the Kraken Browser freezing after Windows sleep/wake. Add a watchdog: track last rAF tick and last monitoring callback; if monitoring stalls >5s or rAF stalls, force a re-render / re-subscribe. Also handle `visibilitychange` and `pageshow`.

DISTRIBUTION:

10. Ship a one-click install button in the README and on the config page: `https://cam-redirect.nzxt.com/action/load-web-integration?url=https://<user>.github.io/<repo>/` (and the `cam-beta-redirect` variant). This is the established convention for every community project and dramatically lowers setup friction versus "paste this URL into CAM."

11. Static-only hosting keeps us eligible for official NZXT submission (they only accept statically hostable integrations; anything needing a server/OAuth gets relegated to the community list). Avoid any required backend. If we later want now-playing/system data beyond CAM's monitoring feed, follow NZXT-ESC's pattern: optional local companion app over WebSocket, kept strictly optional.

12. Build a browser-mode simulator (mock MonitoringData + a 640x640 circular frame) so the whole thing is developable and demoable without a Kraken — every serious prior-art project does this (kraken-dash's "SIM" marker, NZXT-ESC's mock values).

MUST-VERIFY-ON-HARDWARE LIST (undocumented, do not design around assumptions):
devicePixelRatio in the Kraken Browser; whether CAM applies any circular mask itself; exact Chromium/Electron version and therefore available web APIs (WebCodecs? WebGPU? AVIF?); whether webview audio reaches speakers; reload cadence and whether changing CAM settings reloads the page; localStorage/IndexedDB persistence across full CAM restarts and CAM updates; Kraken Plus (2025) reported width/height/shape; actual achieved FPS for a video-heavy frame vs a flat-color frame at max slider.
